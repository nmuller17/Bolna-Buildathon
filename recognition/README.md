# recognition (P3): sign classifier

**Validation status (2026-10-10):** the local `model.pt` is trained on synthetic data only. Accuracy figures in the existing reports are synthetic or awaiting benchmark audit, including signer-overlap checks. Do not use them in slides or claim real guest accuracy. The tests below establish pipeline behavior, not sign-language accuracy.

This module turns one segmented sign, given as a list of MediaPipe landmark frames (from the Python MediaPipe library on the laptop, or from the browser), into the three most likely labels out of the 22 classifier classes in `docs/vocabulary.md` section 3. It never sees video: MediaPipe runs first and only landmark coordinates reach the classifier, which keeps the guest's face and surroundings out of it and keeps the model small enough to run on a laptop CPU.

The pipeline is the same for training and serving. Each frame is re-normalized with the CLAUDE.md 6.2 rule (shoulder midpoint as origin, shoulder distance as unit), which is harmless if capture already did it and corrects any upstream difference. Each hand is given to `lh` or `rh` by whichever pose wrist it is closer to, so it does not matter how the landmarker labels handedness. The frames are then turned into a fixed 141-number row per frame (hand position and shape, upper body and nose; face landmarks are not used; layout documented at the top of `features.py`), resampled to 32 time steps, and passed to a small bidirectional GRU. A temperature fitted on a held-out signer may soften overconfident answers (T of 1 or more) but is never allowed to sharpen them, because sharpening on one easy validation signer made the model confidently wrong on a harder one.

## Data layout expected from capture.py

Training files go in `data/train/<LABEL>/<signer>_<n>.json`, where `<LABEL>` is exactly one of the 22 labels (for example `THANK-YOU`, `FS-WIFI`, `NONE`). Each file can be either a plain `Frame[]` list or a SignFile dict with a `frames` key (CLAUDE.md 6.1 and 6.3). The signer is taken from the SignFile `signer` field when there is one, otherwise from the file name (everything before the last underscore). Getting the signer right matters: the benchmark holds out one whole person at a time, and if every take looks like a different person it silently becomes optimistic, so the loader warns when the signer count looks wrong. Folders with unknown labels are skipped with a warning, files without any pose are skipped, parts with the wrong number of points are reported, and classes with no or very few takes are reported when loading.

## Commands

All commands run from the repository root with the project venv (`source .venv/bin/activate`). The server needs only the root `requirements.txt`; tests also need `pip install -r recognition/requirements-test.txt`.

```bash

python -m recognition.train --data data/train --refit-all
# if the benchmark shows the simple baseline beating the GRU, train and serve that instead (same file, same server)
python -m recognition.train --data data/train --refit-all --model baseline

# benchmark: leave-one-signer-out, GRU vs baseline, latency -> recognition/reports/benchmark_team.md
python -m recognition.benchmark --data data/train --tag team

# evaluate a saved model on a separate folder in the same layout
python -m recognition.benchmark --checkpoint recognition/models/model.pt --test-data data/heldout --tag heldout

# serve (loads recognition/models/model.pt once at startup; it must match recognition/model_pin.py)
uvicorn recognition.server:app --host 127.0.0.1 --port 8000
# before the H13 pin, development only: RECOGNITION_ALLOW_UNPINNED=1 uvicorn recognition.server:app ...
# LAN / iPad: this launcher refuses a non-local host unless RECOGNITION_TOKEN is set, and without TLS

  python -m recognition.server --host 192.168.1.20 --ssl-certfile cert.pem --ssl-keyfile key.pem   # e.g. mkcert

# serve a mock so P4 is never blocked (no model needed; every 5th frame count gives a low-confidence answer)

# tests
python -m pytest recognition/tests -q
```

The API is `POST /predict` with `{"frames": Frame[]}` returning `{"top": [{"label", "conf"} x 3]}` sorted by confidence, and `GET /health` returning `{status, model_loaded, classes, mock}` to a caller on the laptop or one sending the token (anyone else gets only `{status}`). The schema is strict: malformed input gets 422 (unknown keys such as `leftHand`, wrong point counts, strings or booleans instead of numbers, NaN, coordinates beyond plus or minus 50, an empty list, more than 300 frames). Bodies over 4 MB get 413, more than 8 requests at once get 429, a wrong or missing token gets 401 (checked before the body), an unknown `Host` header gets 400, and a missing or unloadable model gets 503. P4 should treat every non-200 answer like low confidence. The model is skipped and `NONE` is returned with confidence 0.98 when fewer than 10% of the frames contain a hand, or when fewer than 30% of the frames contain both shoulders (without shoulders the coordinates cannot be normalized, and the model would otherwise give confident nonsense).

## Python MediaPipe input

Live landmarks and training captures now come from the MediaPipe Python library, so the classifier's input is MediaPipe Python output. Three pieces turn it into predictions in the same process, with no HTTP: `mediapipe_adapter.FrameAdapter` converts each landmarker result into one Frame (CLAUDE.md 6.1, normalized per 6.2), `segmenter.Segmenter` cuts the stream into signs and utterances (CLAUDE.md 7.2 step 2), and `recognizer.Recognizer` returns the top 3 for a sign using exactly the same checks as `POST /predict` (the server calls the same function). The adapter reads tasks `HolisticLandmarker` results (mediapipe 1.1.0, which no longer has `mp.solutions`), legacy `mp.solutions.holistic` results, or a `PoseLandmarker` result plus a `HandLandmarker` result; hands always go to `lh`/`rh` by the nearest pose wrist, never by MediaPipe's handedness label. None of these modules imports mediapipe when imported, and the server never needs it.

The simplest way to use them together is `stream.SignStream`, which also adds the framing gate, capture-parity cleaning and timestamps (section "Live stream" below):

```python
from recognition.mediapipe_adapter import load_holistic
from recognition.recognizer import Recognizer
from recognition.stream import SignStream

landmarker = load_holistic()                      # recognition/models/holistic_landmarker.task, VIDEO mode
stream = SignStream(Recognizer(), image_size=(width, height))   # Recognizer(mock=True): no model
for t, rgb in camera_frames():                    # your loop: capture time in s, UNMIRRORED RGB frame
    for event in stream.detect(landmarker, rgb, t):
        send_to_app(event)                        # "sign" / "utterance" / "framing" dicts (App bridge below)
```

Underneath, per frame: `frame = FrameAdapter(image_size=(w, h), mode="capture")(result)`, then `Segmenter(y_scale=adapter.y_scale).push(frame, t)`; a sign event is a tuple `("sign", frames)` that also carries `.times` (capture time of each frame), and `Recognizer().predict(cleaned_frames)` gives the top 3.

Rules that matter:

- **Unmirrored frames.** Give MediaPipe the camera image exactly as captured; mirror only the on-screen preview. On an unmirrored image the person's left shoulder (pose 11) and left hand appear on the image right; mirroring swaps every left/right label.
- **Minimisation is on by default.** `FrameAdapter()` returns `face: None` and overwrites pose points 1 to 10 (eyes, ears, mouth corners) with a copy of the nose (pose 0), so a frame holds no facial landmark beyond the nose position the model already uses. The model reads only pose 0 and 11 to 16 plus the hands, so its output is identical either way (tested). `FrameAdapter(minimize=False)` keeps them and returns the 26 face points, which is only for avatar captures (P2).
- **Same frames as the training captures.** `FrameAdapter(image_size=(w, h), mode="capture")`, which `live.py`, `classify_video.py` and `stream.SignStream` use by default, returns exactly `capture.landmarks.normalize(capture.landmarks.to_frame(result, w / h))`, calling the teammate's own code (x and z times width/height, origin = shoulder midpoint in x and y, z only scaled, rounded to 5 decimals), and `None` for a frame without pose, as `capture.py` does; minimisation is applied after that. Each closed sign is then extended over the hand-visible frames around it and cleaned with `capture.clean.clean` and the real frame times, as `capture.py` cleans a take (see "Live stream" below). The default `mode="legacy"` (the earlier conversion, kept for `recognition/compare`) does neither. Training captures and live input should also use the same camera resolution (`live.py` asks for 1280x720, as `capture.py` does), the same mediapipe version and the same `holistic_landmarker.task` (`live.py` warns when `capture/models/` holds a different one).
- **Streams.** Use one `FrameAdapter`, one `Segmenter` and one VIDEO-mode landmarker per camera stream. Capture mode returns `None` when a pose is missing; only legacy mode reuses the last shoulders. The segmenter keeps timing state. Pass each frame's capture time to `seg.push(frame, t)`: speeds and timings are then in real seconds however fast the landmarker runs (without `t`, frame i is taken to be at i / fps). Pass `y_scale=adapter.y_scale` so the signing area is in real shoulder widths whatever the camera's aspect ratio. Call `seg.flush()` at the end of a video file. The in-process recognizer converts a missing whole frame to a Frame with all parts null before validation; `/predict` still requires Frame objects under the protected team contract.
- **Still images.** A `HolisticLandmarker` keeps state between calls even in IMAGE mode: it raises on an image of a different size and can return a different result for the same image on the next call. Use `mediapipe_adapter.detect_image(rgb)` (a fresh landmarker per image) for photos, and to compare two settings convert the same result twice instead of detecting again.
- **Segmenter thresholds** (named constants at the top of `segmenter.py`) are first guesses, not frozen. A hand counts when its wrist is within 2 shoulder widths of the body midline and no lower than 1.0 real shoulder widths below the shoulder line (about the navel). Motion is the larger of the hand's travel and the change of its fingertip-to-wrist distances (so NO and fingerspelling count), smoothed and measured over about 0.17 s. A sign starts when a hand moves faster than 0.5 shoulder widths per second, or when a hand enters the area (the sign must still exceed 0.5 at some point); it closes after 0.5 s of pause or hands down; less than 0.25 s of movement or 0.2 shoulder widths of travel is discarded; a sign reaching 300 frames is force-closed; the utterance ends after 1.5 s with no hand in the area (or 3 s of hands resting still in it). On GISLR clips of 30+ frames padded with 1 s of hands-down frames (`tests/test_segmenter_gislr.py`, run with `-s` for the table) it finds a sign in 269 of 366 clips (73%; NO 27/43, lowest label TIME 60%), up from 157 (43%; NO 8/43) for the first version. GISLR clips are cut tightly to the sign, so this is a pessimistic bound, and about 3% of clips are split into two signs. It is not our webcam: re-tune on the first real takes with `python -m recognition.classify_video take.mp4 --mock --trace`, which prints the motion and wrist positions per frame. On a test photo of a seated person, the wrists resting on the knees were 0.8 to 0.95 real shoulder widths below the shoulders, inside the area, so resting hands end an utterance through the 3 s rule.

Two reference command lines (they need mediapipe and opencv-contrib-python from `requirements.txt` and the model file: `curl -L -o recognition/models/holistic_landmarker.task https://storage.googleapis.com/mediapipe-models/holistic_landmarker/holistic_landmarker/float16/latest/holistic_landmarker.task`):

```bash
python -m recognition.classify_video clip.mp4 [--mock] [--json] [--trace]
python -m recognition.live --camera 0 [--post http://127.0.0.1:3000/api/guest/signs] [--mock] \
    [--utterance-gap 1.5] [--sign-gap 0.5] [--waist hips|none]
```

Both print the same events (below) and a latency summary; `--json` also prints each event as JSON. `classify_video` times a file as if a camera delivered it live (event times are seconds from the start of the clip, plus the real processing time) and warns when MediaPipe is slower than the clip's frame rate. The benchmark's in-process HTTP client identifies itself as `127.0.0.1` so latency measurement uses the same loopback-only policy as the app.

## Live stream: framing, timing and latency

`stream.SignStream` is the whole guest-side pipeline for one camera: per frame it checks the framing on the raw MediaPipe pose (`framing.py`), converts the result in capture mode, and feeds the segmenter. When a sign closes it is classified at once and a `sign` event is emitted; the utterance event follows when the hands have been down for `--utterance-gap` seconds.

- **Matching a training take.** A `capture.py` take keeps every frame of its 2 s window in which a hand is visible (`clean.trim`), then resamples to 30 frames/s, forward-fills missing hands and smooths over 3 frames. The live segment is therefore extended over the contiguous hand-visible frames just before it (at most 0.5 s, never into the previous sign) and just after it (up to the frame that closed it, so no extra delay), then cleaned by `capture.clean.clean` with the real frame times. Tested on synthetic takes (`tests/test_stream.py`): when the hands come up from out of the picture, the live segment equals the training file exactly at a steady 30 frames/s; with irregular frame times one nearest-neighbour pick can move by a frame, because capture's 30 frames/s grid starts at the take's first frame (mean feature difference below 0.005). When the hands rest in view the whole time, a take keeps its whole window and the live segment cannot know where that window was, so the cut differs. How much depends on when the signer starts after GO: on a clip run through the real HolisticLandmarker (hands resting in view, the live segment 70 frames), 2 s takes starting 0 to 30 frames before the sign give a mean feature difference of 0.010 to 0.030 (maximum 0.26 to 0.37); only the best-aligned window is near 0.01 (the synthetic test, sign centred: 0.008). Only re-cutting the training takes with the live segmenter removes this, which needs the raw frames and times of each take (requested from P2). Real takes have not been compared yet.
- **Framing (head to waist).** A frame is `OK` when the nose, both shoulders, elbows, wrists and hips (the waist) are inside the picture with a 3% margin and MediaPipe's presence is at least 0.5, the picture reaches 0.4 shoulder widths above the nose (about the hairline; the margin adds the rest) and the shoulder width is at least 0.12 of the shorter side of the picture. Otherwise it is `STEP_BACK` (head or hips cut and the body does not fit, or the signing space is wider than the picture), `MOVE_CAMERA_DOWN` (hips below the picture with room above the head), `COME_CLOSER` (the person is so small that the hands are only a few dozen pixels; it is also shown instead of `NO_PERSON` for 3 s after a small person was seen, because MediaPipe loses a person who is very far away), `CENTER`, `HANDS_OUT` (a wrist or elbow outside) or `NO_PERSON`. MediaPipe invents points: with the head cropped off it put the nose inside the picture at shoulder height with presence 1.0, so the head also counts as cut when the nose is less than 0.25 shoulder widths above the shoulders, and the hips when they are less than 0.8 shoulder widths below them. A nose inside the picture is not enough: cut just above the nose (eyes and forehead out) the photo used to pass, which is why the headroom rule exists. The thresholds are first guesses from photos; tune them on webcam frames. A sign is classified only when at least 80% of its frames are `OK`; otherwise a `framing` event with the most common problem replaces the prediction and the utterance asks for a repeat. `--waist none` drops the hips from every rule, for a counter that hides them; it is a fallback, because the model was trained on head-to-waist takes. On the test photo (a seated person, hips visible, 960x640) the status is `OK`; cropped at chest height, just above the hips, through the eyes or mid-forehead it is `STEP_BACK`; cropped just above the hair, or at the knees, `OK`; cut at a side `CENTER`; shrunk onto a 1280x720 canvas it is `OK` down to shoulders of 96 pixels and `COME_CLOSER` at 79 and 61 pixels (MediaPipe finds no person at about 50). `live.py` draws the margin box (green when `OK`) and the guidance text on the mirrored preview.
- **Latency.** Every sign event carries `t_sign_start` and `t_sign_end` (capture times of the first frame and of the last frame that was still moving), `t_closed` (when the segmenter decided, which is about `--sign-gap` later plus the processing of that frame) and `t_predicted`. `t_predicted - t_sign_end` is the true delay from the end of the movement to the answer. `live.py` prints p50/p95 of MediaPipe time per frame, predict time, close delay and total after each utterance, every 10 s and at exit. A reader thread keeps only the newest camera frame, so a landmarker slower than the camera skips frames instead of falling behind. Measured with `classify_video` on an M2 Pro under load from other jobs (load average about 9 to 14 on 10 cores), on two 1280x720 clips made from a photo (not real signing) with the synthetic model: MediaPipe 33 to 35 ms per frame (p50; p95 35 to 45), predict 15 to 34 ms p50 with spikes to about 120 ms (the model itself takes 2 to 5 ms; the rest is the strict input validation and load), close delay 535 ms (p50, default `--sign-gap 0.5`) or 331 to 334 ms (`--sign-gap 0.3`), total 573 to 584 ms or 372 to 384 ms. MediaPipe at 33 to 35 ms is right at the 33 ms frame interval of a 30 frames/s camera, so on a loaded machine some frames are skipped. The utterance ends `--utterance-gap` seconds after the hands leave the signing area (default 1.5; aim for 0.8 to 1.0 once tuned on real takes) or, with the hands resting still inside it, twice that.

## App bridge (recognizer to app)

`live.py --post URL` sends every event as its own `POST` with `Content-Type: application/json` and the header `X-Bridge-Key: <BRIDGE_KEY>`. `live.py` refuses to start with `--post` unless the environment variable `BRIDGE_KEY` holds at least 32 characters (the app disables the route for shorter keys), and the key is never printed or logged. `--post` only accepts a loopback URL (127.0.0.1, ::1 or localhost) unless `--post-allow-remote` is given with an `https://` URL. Redirects are not followed and proxies are not used, so the key only goes to the given URL. No video and no landmarks are ever sent. Times are Unix seconds (float, millisecond precision) taken from a monotonic clock, so they can be compared with the app's `Date.now() / 1000` on the same machine.

Delivery runs in one worker thread, so recognition never waits for the network:

- `sign`, `utterance` and `framing` events with `rejected_seq` are sent first, in order, from a queue of at most 64 (the oldest is dropped when it is full), with a 1 s timeout.
- Other `framing` events and `status` events are coalesced: only the newest of each waits, it is sent only when no sign or utterance is waiting, and its timeout is 0.3 s.
- An event that has waited more than 5 s is not sent at all, so an app that comes back after being down does not get a replay of old signs.
- Every body carries `t_sent` (Unix seconds when it left the recognizer); the app should also discard events whose `t_sent` is more than a few seconds old.
- The app's answer to the first event is printed once (a 401 or 403 adds a hint to check `BRIDGE_KEY`); later failures are printed at most every 5 s. At exit `live.py` prints how many events were sent, failed, dropped, stale and coalesced.

With an app that takes 3 s to answer every request, sign events still reached it within 0.01 s of `t_predicted` and utterances within 0.3 s of `t_end` (before this change, the fifth sign arrived 9.5 s late).

Shutdown drains the queue for at most 2 s, then discards remaining events; an in-flight request may finish within its own timeout. Delivery is best effort: the app must handle missing sequence numbers, reject stale events after ending a guest session, and require confirmation before speaking.

```json
{"type": "sign", "seq": 3, "top": [{"label": "TOWEL", "conf": 0.82}, {"label": "MORE", "conf": 0.09}, {"label": "NONE", "conf": 0.04}],
 "t_sign_start": 1760112001.204, "t_sign_end": 1760112001.951, "t_closed": 1760112002.488, "t_predicted": 1760112002.503, "t_sent": 1760112002.504}
{"type": "utterance", "signs": [{"label": "MORE", "conf": 0.91}, {"label": "TOWEL", "conf": 0.82}, {"label": "PLEASE", "conf": 0.44}],
 "seqs": [2, 3, 4], "needs_repeat": true, "t_end": 1760112004.371, "t_sent": 1760112004.372}
{"type": "framing", "status": "STEP_BACK", "since": 1760112010.120, "t_sent": 1760112010.621}
{"type": "framing", "status": "HANDS_OUT", "since": 1760112012.003, "rejected_seq": 5, "t_sent": 1760112013.140}
{"type": "status", "fps": 27.4, "recognizer": "ok", "t": 1760112013.000, "t_sent": 1760112013.001}
```

- `sign`: sent the moment a sign closes, before the utterance ends; `seq` counts signs from 1 for the process. `top` is the top 3, best first, exactly as `POST /predict` would answer.
- `utterance`: the top-1 of each sign of the utterance, in order, with their `seq`s; 1 to 8 signs. An utterance that reaches 8 signs is ended at once (the app accepts at most 8 per POST) and the next sign starts a new one. `needs_repeat` is `recognizer.needs_repeat` (true when any sign is `NONE` or below 0.6, CLAUDE.md 7.2 step 4), the same rule the app applies for display, so both agree. Every utterance is sent, including the ones that need a repeat: the app shows "Could you repeat?" for those and must not speak them.
- `framing`: the framing status changed and has held for 0.5 s (`OK`, `STEP_BACK`, `MOVE_CAMERA_DOWN`, `COME_CLOSER`, `CENTER`, `HANDS_OUT`, `NO_PERSON`; `since` = when it started), or, with `rejected_seq`, a sign was not classified because fewer than 80% of its frames were framed `OK`. A rejected sign stands in its utterance as `{"label": "NONE", "conf": 0.0}`, so that utterance always needs a repeat. Suggested guest text is `framing.GUIDANCE`.
- `status`: at most once a second: processing rate and `recognizer` = `ok`, `mock` (invented answers, never speak them) or `no_model` (no checkpoint or a pin mismatch: no `sign` events, framing still works).
- Every event also has `t_sent`. The app should check `type` and ignore unknown keys.

## Video call (screen source, Option A)

This lets SignBridge work inside any video call (Zoom, Microsoft Teams, Google Meet, FaceTime) without a platform API. The Deaf guest calls the hotel laptop. Their video tile is already on the laptop's screen, so `live.py --source screen` reads that tile from the screen instead of a webcam and sends it through exactly the same pipeline as the camera (framing gate, capture-parity frames, segmenter, cleaning, Recognizer, the same events and `--post` bridge). The other direction (the avatar answering the guest) is a page shared into the call by the web app and is not part of this module.

```bash
pip install mss pyobjc-framework-Quartz            # screen source only; the server does not need them
python -m recognition.live --source screen --list-windows
python -m recognition.live --source screen --window-name zoom.us --say
python -m recognition.live --source screen --window-name zoom.us --region 640,40,640,360   # one tile of the window
python -m recognition.live --source screen --region 100,100,1280,720 --fps 15
RECOGNITION_ALLOW_UNPINNED=1 python -m recognition.tools.screen_bench capture/reference/HELP.mp4   # speed check, no permission needed
```

- **Choosing what to read.** `--window-name` picks the largest normal on-screen window whose application or title contains the text, ignoring case (`zoom.us`, `Microsoft Teams`, `Google Chrome` for Meet, `FaceTime`); `--list-windows` prints them with their positions. `--region x,y,w,h` alone is a rectangle of the screen in points (the numbers `--list-windows` and Cmd+Shift+4 show); together with `--window-name` it is relative to the window's top-left corner, which is how one participant's tile is selected. With neither, the whole main display is read. The window's position is re-read every second, so it can be moved; its size is fixed at start because the landmarker needs one picture size per stream (resizing prints a warning; restart to re-measure). A window that is closed or minimized stops the source after 2 s.
- **What is read is the screen as composed.** Anything on top of the rectangle (a notification, another window, the recognizer's own preview) is read too, so the preview is off by default in screen mode (`--preview` turns it on, unmirrored). Keep the call window visible. In a one-to-one call use the view that shows the guest large, and hide your own self-view (Zoom: right-click your video, Hide Self View) or crop it out with `--region`, otherwise MediaPipe may find the receptionist in the self-view thumbnail.
- **Picture size.** Frames are delivered at the captured pixel size, scaled down to at most 1280 pixels wide (a Retina screen can give twice the points). The framing gate and capture mode's aspect scaling use this size, so a tile that is not 16:9 is measured correctly, but a warning is printed because the training takes were 16:9; another warning is printed below 360 pixels tall, where the hands become very small. The framing rules still apply: the guest must be framed head to waist in their own camera (`--waist none` only where a desk hides the hips).
- **Mirroring.** The training takes are unmirrored camera pictures. Zoom, Teams, Meet and FaceTime mirror only your own self-view; other participants are shown as their camera sends them, so the default is no flip. `--mirror` flips each frame for a source that shows a mirror image. This is the vendors' documented behaviour and has not yet been checked on a live call. Hands are assigned by the pose wrists and training uses random left/right mirroring, so a wrong choice costs little.
- **macOS Screen Recording permission.** Reading another app's window needs it for the app that started Python (Terminal, iTerm2, Visual Studio Code...): System Settings > Privacy & Security > Screen & System Audio Recording, switch the terminal on, then quit and reopen it. `live.py` checks this first (`CGPreflightScreenCaptureAccess`, which does not prompt) and stops with these instructions. Without the permission macOS hides other apps' pixels (a test capture of another process's window returned only the desktop picture) and window titles (`--list-windows` still shows the application names). A process may read its own windows without it, which is how `tools/screen_bench.py` measures speed.
- **Captions and voice.** In screen mode each utterance prints a `CAPTION` line. `--say` also speaks it on the laptop with a macOS system voice, using the app's fixed guest sentences (`docs/vocabulary.md` section 2, where checkout is the sign `LEAVE`; `FS-CHECKOUT` from a checkpoint trained before the rename is mapped to `LEAVE`, as `web/app/api/english` does). The app's rules apply: an utterance that needs a repeat is captioned as unclear and not spoken; mock answers are never spoken; clear signs that match no fixed sentence are captioned but not spoken, because this demo does not call Claude. Intent 4 (NAME plus a typed name) is not handled. Speech is local only (no ElevenLabs, no cloud): with pyobjc installed one `NSSpeechSynthesizer` is kept open and warmed up silently at start (`--say-engine auto`, the default), otherwise each sentence runs the `say` command. `--say-voice Daniel` picks a voice.
- **Privacy.** No new data flow is created: the guest's video already reaches the laptop through the call. Frames are read into memory, turned into landmarks and dropped; nothing is written to disk, nothing is sent anywhere except the events to a loopback `--post` URL, and no ports are opened, no tunnels and no call-platform keys are used. The guest should still be told that the laptop is reading their video to interpret signs (the page shared into the call should carry that consent notice).

Measured with `tools/screen_bench.py` on this M2 Pro while other jobs kept the load average at 21 to 25 on 10 cores (much heavier than for the numbers in "Live stream" above), reading a 1280x720 OpenCV window that played `HELP.mp4` (480x270 scaled up) from the same process, synthetic `model.pt` (labels meaningless; plumbing and speed only):

| What | 20 frames/s target | 15 frames/s target |
|---|---|---|
| Grab and convert one 1280x720 frame, p50 / p95 (pacing off; measured before each run) | 18 / 26 ms | 13 / 20 ms |
| Frames captured per second | 16.0 to 18.2 | 13.9 |
| Frames processed by MediaPipe per second | 10.1 to 14.3 | 11.9 |
| From `imshow` to the frame being captured, p50 / p95 | 34 to 35 / 58 to 62 ms | 33 / 55 ms |
| MediaPipe per frame, p50 / p95 | 60 to 68 / 131 to 157 ms | 61 / 142 ms |
| End of movement to prediction, p50 / p95 (3 signs, `--waist none`) | 1535 / 2257 ms | no sign classified |

Under that load MediaPipe took about twice its usual 33 to 35 ms, so the landmarker, not the screen capture, limited the rate; the predict step (415 ms p50 here, 2 to 5 ms for the model itself) suffered most. The reference clip is framed chest up, so with the default `--waist hips` every frame was `MOVE_CAMERA_DOWN` or `STEP_BACK` and every sign was rejected, which is the gate working as designed; with `--waist none` 54% of frames were `OK` and 46% `HANDS_OUT`. The call's own network delay (guest camera to laptop screen) is not included and was not measured. Speech: `say -o file hi` took 1.8 to 2.5 s per run (process start and voice loading), against 0.78 to 0.86 s for the whole sentence "Where is the elevator?" through the warm synthesizer (time until it finished, measured near zero volume). Repeat the table on an idle machine and on a real call before quoting it.

## Privacy and security defaults

The server never logs request bodies or landmarks, never writes incoming frames to disk, and does not echo submitted data or file paths back in errors. The model does not use face landmarks at all, so the browser may send `face: null` and the prediction is unchanged. It binds to 127.0.0.1, and when `RECOGNITION_TOKEN` is not set it answers 403 to any client whose socket address is not on the laptop itself (127.0.0.1 or ::1), whatever address uvicorn was started on. It accepts only `Host: localhost` or `127.0.0.1` (plus `RECOGNITION_ALLOWED_HOSTS`), which blocks DNS-rebinding pages, and CORS only allows the origins in `RECOGNITION_ALLOWED_ORIGINS` (default `http://localhost:3000,http://127.0.0.1:3000`). If you need to reach it from an iPad or another device on the network, use `python -m recognition.server --host <LAN address> --ssl-certfile ... --ssl-keyfile ...`, which refuses to start without `RECOGNITION_TOKEN` (and without TLS unless `--insecure-http`); the token must then be sent in the `X-Recognition-Token` header, and the laptop's LAN address must be added to the host and origin allowlists. A token sent from browser code is visible to anyone using that browser, so it only keeps out other devices on the network, not the person at the screen. Never put port 8000 behind a tunnel such as ngrok. At the H13 freeze, pin the demo model with `python -m recognition.pin_model recognition/models/model.pt` and commit `recognition/model_pin.py`: the server and `Recognizer` then refuse any other file (the log says "hash mismatch", `/predict` answers 503, `Recognizer` raises). The pin is a constant in git, never read from the models folder and with no environment override. Until it is set, the loader fails closed: it refuses every checkpoint ("model not pinned: refusing") unless `RECOGNITION_ALLOW_UNPINNED=1` is set for development, and that variable never overrides a pin that is set. `holistic_landmarker.task` is pinned the same way (`EXPECTED_TASK_SHA256` in `mediapipe_adapter.py`) and loaded from the bytes that were checked, because its download URL is a mutable `latest`. A LAN bind also needs TLS (`--ssl-certfile`/`--ssl-keyfile`, for example from mkcert) unless `--insecure-http` is passed on an isolated network, because otherwise the token and guest landmarks cross the network in clear text. Face points sent by a client are dropped before the model. Importing `recognition.server` loads nothing: `app` builds itself when uvicorn starts. The red-team regression tests are in `recognition/tests/security/`. Checkpoints are loaded with `torch.load(weights_only=True)`, so a tampered `model.pt` passed around on chat cannot run code; a checkpoint from an older `train.py` is refused and must be retrained. `RECOGNITION_MODEL` points the server at a different checkpoint, and `RECOGNITION_MOCK=1` is announced in the log and in `/health` so it is not left on by accident.

## Reading the benchmark report

`recognition/reports/benchmark_<tag>.md` starts with a summary table comparing the GRU with a simple baseline (logistic regression on per-take averages, spreads, minima and maxima). Every metric is defined in plain words at the bottom of the report. The most important numbers for the demo are the accuracy on accepted answers and the "wrong sign spoken" rate: the first says how often the system is right when it is confident enough to speak, and the second says how often it would confidently say something the guest did not sign. Leave-one-signer-out numbers describe a person the model has never seen; a team member who also recorded training data will usually do better live. The per-class recall table shows which signs need more or cleaner captures, and the confusion matrix shows which pairs get mixed up. The "wrong sign spoken at T=1" row shows what the temperature changes, and the unknown-sign section (baseline only, because it needs one retraining per sign) estimates how often a sign outside the vocabulary is spoken as one of ours; on real data this is usually high, which is why broad `NONE` captures matter. If the GRU does not beat the baseline clearly on real captures, the deep model is not earning its keep on that data; the baseline also looks at the three thirds of each take separately, so it can tell movement direction. Reports made with the tag or data path containing "synthetic" carry a banner, because those numbers only prove that the code runs.

## Known limitations

- The local checkpoint is synthetic. Planned team captures are from hearing, non-native signers; real performance needs a held-out signer, preferably a Deaf or fluent signer, plus varied `NONE` examples.
- It recognises isolated signs from a closed list of 21 plus `NONE`. It depends on the segmenter (`segmenter.py`, or the browser one) cutting one sign per segment and cannot follow continuous signing.
- Training captures and live landmarks should now both come from Python MediaPipe, which removes most of the browser-versus-Python skew, but only if both use the same mediapipe version and the same landmarker. On one test photo the HandLandmarker hand points differed from the HolisticLandmarker ones by up to 0.056 shoulder widths, and on a second photo Holistic found no hands where HandLandmarker found both. If the browser path is ever used again, record a few takes through it and evaluate them with `--checkpoint ... --test-data ...`.
- `capture.py` and capture mode multiply x and z by width/height before normalizing, so the shoulder normalization is no longer skewed by the camera's aspect ratio; a different camera or resolution still changes the field of view and MediaPipe's accuracy, so capture and live should use the same camera at 1280x720. Training files made without the aspect scaling (for example by an older capture.py) would not match and must be re-captured.
- Browser selfie views are usually mirrored, and MediaPipe hand labels depend on whether the image was flipped. Hands are reassigned by the pose wrists, and training uses random left/right mirroring so the model tolerates a mirrored body and left-handed signers, but the browser should still feed MediaPipe the unmirrored camera image (mirror only the on-screen preview).
- A closed-set classifier will often speak a confident wrong word for a sign it was never trained on. Record varied `NONE` takes, and consider adding public out-of-vocabulary signs as `NONE` (`--oov-none`, below).
- `recognition/models/model.pt` is gitignored; whoever trains the demo model must share it with the person running the server.

## Public data

Only one public dataset is usable in the time we have: Kaggle "Google - Isolated Sign Language Recognition" (GISLR, 2023). It ships MediaPipe Holistic landmarks only (no video), in the same image-normalized, y-down coordinates we use, for 250 signs. Seven of our 21 signs are among them: `yes`, `no`, `please`, `thankyou`, `where`, `time`, `room` (checked against the 250-sign map downloaded from Kaggle). The other 14 (RESERVATION, NAME, ELEVATOR, FS-WIFI, PASSWORD, BREAKFAST, TOWEL, MORE, FS-CHECKOUT, LATE, PARKING, TAXI, HELP, RESTAURANT) are not in it, so it cannot replace our own captures.

- **Access.** The competition train set (about 40 GB, reported elsewhere, not checked) needs a Kaggle account and accepting the rules. A labelled re-run copy published by Kaggle staff (dataset `sohier/461054610546105`, 39,443 sequences, 10 participant IDs) can be downloaded file by file without logging in; we checked that both the labels file and a landmark file download (HTTP 200). Our 7 signs there are 1,105 sequences from 8 to 10 people per sign (about 556 MB by Kaggle's file listing). `--download` fetches exactly those (plus `--oov-none N` takes of every other sign if asked).
- **Licence.** The data card says CC BY 4.0, but the competition rules forbid redistributing the data. So: train on it and share model weights with attribution, but keep raw and converted files in the gitignored `data/` folder and never commit them or put them in `signs/`.
- **Signers.** The data card describes 21 Deaf signers who use ASL as their primary form of communication, recorded on Pixel 4a phones, some signing with the left hand and some switching hands. That makes it most useful as an honest test on people who are not on our team: train on team data, then run `python -m recognition.benchmark --checkpoint recognition/models/model.pt --test-data data/gislr --tag gislr` (it only scores the 7 shared signs, and the other 14 classes simply never appear).
- **Format details.** Each parquet has 543 rows per frame (face 468, left hand 21, pose 33, right hand 21), and a hand that was not detected is 21 rows of NaN, which the converter writes as `null`. The frame rate is not stated (30 fps is assumed), and the clip aspect ratio is not given, so x and y are scaled differently from our webcam.
- **Other datasets checked and not used.** ASL Citizen covers 15 of our signs but its Microsoft Research licence forbids redistributing the data and allows non-commercial research only; WLASL covers 15 but is video scraped from third-party sites with many dead links and a non-commercial licence; PopSign has the same 250 signs as GISLR as raw video only; the Kaggle fingerspelling set is continuous character sequences, not whole-word `FS-WIFI` or `FS-CHECKOUT` units.
